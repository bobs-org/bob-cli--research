**Obsidian Vim yank feedback: exact ranges, a short flash, and a narrow compatibility adapter**

Independent research by **cdx**, 2026-11-11. No other report or researcher's findings from this swarm were consulted. This is a design investigation; no plugin, vault configuration, clipboard behavior, or production code was changed.

**Decision in brief.** This is a good idea: a brief highlight confirms both that a yank happened and which text it used, without requiring a selection-first workflow. I recommend a small, separately disableable **Bob Vim Yank Highlight** plugin in `bob-plugins`, using CodeMirror decorations and the ranges selected by the native Vim engine. Start with SASE's 200 ms duration. The hard part is obtaining trustworthy ranges from Obsidian's bundled Vim implementation, not drawing the highlight. Existing plugins provide useful precedents, but the implementations inspected have enough correctness or lifecycle weaknesses that I would not adopt them unchanged as the durable solution.

**What SASE actually does.** At SASE commit `7cc41d89ab321e67bb3b594030d654a348d33aa5`, `YankHighlightMixin` stores the exact copied span, refreshes an overlay immediately, and clears it after **0.2 seconds**. Every new yank replaces the previous span and increments a generation; obsolete timer callbacks cannot clear a newer flash. The color comes from the active theme's success color, with foreground text and bold styling. Yank callbacks live in the characterwise and linewise operator implementations after the register is populated. Delete and change operations do not invoke the flash. Empty spans do not flash, and large buffers skip the overlay. These are facts from the implementation, rather than assumptions about the visual example. [SASE overlay implementation](https://github.com/sase-org/sase/blob/7cc41d89ab321e67bb3b594030d654a348d33aa5/src/sase/ace/tui/widgets/_yank_highlight.py), [operator integration](https://github.com/sase-org/sase/blob/7cc41d89ab321e67bb3b594030d654a348d33aa5/src/sase/ace/tui/widgets/_vim_normal_operator_exec.py).

SASE's tests cover `yw`, `yiw`, `yf)`, counted `Y`, `yy`, visual character/line yanks, replacement by a rapid second yank, stale timers, coexistence with search and syntax highlighting, and exclusion of delete/change. The single-line Vim widget deliberately has an inert hook. I inspected these tests; I did not run SASE's suite. The important transferable contract is “briefly mark the source range without changing editing behavior.” Obsidian does not share SASE's Python/Textual renderer or its custom Vim implementation. [SASE test contract](https://github.com/sase-org/sase/blob/7cc41d89ab321e67bb3b594030d654a348d33aa5/tests/ace/tui/widgets/test_prompt_yank_highlight.py).

One subtle distinction matters: SASE starts clipboard delivery asynchronously and flashes immediately. Its flash is already not proof that the operating-system clipboard accepted the text. Preserve that distinction in Obsidian: this feature should acknowledge a Vim yank, leaving existing clipboard integrations responsible for their own delivery and errors.

**Critique and proposed requirement adjustments.** The benefit is strongest for `yy`, counts, text objects, and long motions whose extent is otherwise invisible. A 200 ms cue is a reasonable starting point because it matches the established SASE interaction, not because there is evidence it is optimal for every person or theme. A permanent highlight, repeated notifications, or a slow animation would add visual distraction to a frequent operation. A visually convincing but incorrect range would be worse than no feedback.

I would make the following changes explicit before implementation:

| Requirement | Recommended interpretation or adjustment | Reason |
| --- | --- | --- |
| “Highlight copied text” | A transient **yank-source** highlight, never Markdown `==...==` or a persistent selection | Preserves note contents, undo history, cursor behavior, and the next command |
| Trigger | Completed native yank operations; include normal and visual yanks when supported | Counting the typed letter `y` confuses operators with motion arguments, register names, and surround gestures |
| Timing | 200 ms by default; replace the previous flash in the same editor | Matches SASE and avoids accumulating visual noise |
| Clipboard | No new clipboard writes, polling, register synchronization, or clipboard-success promise | Clipboard delivery is a separate concern |
| Editing surfaces | Markdown Source mode and Live Preview first | Reading view has no equivalent Vim editing operation; embedded/table/canvas editors require separate verification |
| Visual/block mode | Use the same mechanism for visual yanks; represent block selections as multiple ranges | Avoids inconsistent feedback and false rectangular spans |
| Blank lines | Give a linewise blank-line yank a modest line background; allow no mark for an empty character range | **Deliberate departure from SASE**, which skips empty copied spans; copying a blank line can still be meaningful |
| Hidden/offscreen text | Decorate visible source positions; do not unfold, scroll, reveal syntax, or change mode | A yank should not rearrange the document view |
| Edits during the flash | Clear on document changes or document replacement | A 200 ms acknowledgement does not need sophisticated tracking through edits |
| Accessibility | No animated fade by default; provide an off switch and adjustable duration if needed | A static brief cue avoids unnecessary motion; test contrast in both themes |
| Initial exclusions | Ex `:yank`, arbitrary system copy commands, mobile, legacy CM5, and unsupported embedded editors are not required for the first release | Keeps the promise aligned with the requested normal-mode editing workflow |

For styling, borrow SASE's timing rather than its exact colors or boldness. Changing font weight can alter glyph widths in an editor. Prefer a theme-aware translucent background with unchanged text metrics. Use a separate CSS class so the hue can be adjusted without adding a large settings panel. Linewise yanks may use a line background as a conventional indication of the copied logical line; characterwise yanks should mark only their exact span. The terminal and browser do not need pixel-identical rendering.

**What the editor exposes.** Obsidian provides CodeMirror editor extensions and decorations. Mark decorations style text; line decorations style a line's container. A view plugin can restrict rendering work to visible ranges; a state field can own ranges independently of the viewport. Either is suitable when used correctly. This feature does not require DOM selection manipulation or rewriting the Markdown. [Obsidian decoration documentation](https://docs.obsidian.md/Plugins/Editor/Decorations), [CodeMirror decoration guide](https://codemirror.net/examples/decoration/).

The supported extension registration API does not make every Vim integration point public. Obsidian's own documentation uses a TypeScript escape hatch to access `view.editor.cm`. Bob already accesses `window.CodeMirrorAdapter.Vim` and nested adapter instances. That is existing local precedent, not a stability guarantee. [Obsidian editor-extension communication](https://docs.obsidian.md/Plugins/Editor/Communicating%20with%20editor%20extensions), [Bob Vim Surround](https://github.com/bobs-org/bob-plugins/blob/87b28e1a60ee4aceca1f9f7094ffe06129b81485/plugins/bob-vim-surround/main.js).

I inspected upstream `replit/codemirror-vim` at `c3131c442069cbe762c7d3c78295b2d98e853bc6`:

- Its dispatcher computes the motion/text-object result, resolves inclusive and linewise boundaries, installs the operation's selections, and then calls the native yank operator.
- The yank operator reads `cm.getSelection()` and calls `getRegisterController().pushText(registerName, 'yank', text, linewise, blockwise)` before the dispatcher collapses or restores the selection.
- The CM6 adapter's `getSelection()` joins its individual selections with newlines. `listSelections()` and the underlying CM6 selection ranges retain the individual positions needed for blockwise display.
- `vim-command-done` is emitted by `clearInputState()`, which can run **before** the operation has executed. It is not a trustworthy post-yank notification.
- I found no dedicated native `vim-yank` event carrying editor identity and ranges in this snapshot. The upstream highlight feature request remains listed as open in the retrieved issue page.
- Ex `:yank` is a separate implementation: it reads a line range with `getRange()` and pushes text directly. An adapter must not assume that every `'yank'` register write corresponds to the current editor selection.

These are the decisive technical constraints. [Native dispatcher and yank operator](https://github.com/replit/codemirror-vim/blob/c3131c442069cbe762c7d3c78295b2d98e853bc6/packages/codemirror-vim-core/vim.js#L2002), [adapter range access](https://github.com/replit/codemirror-vim/blob/c3131c442069cbe762c7d3c78295b2d98e853bc6/packages/codemirror-vim/src/cm_adapter.ts#L271), [Ex yank path](https://github.com/replit/codemirror-vim/blob/c3131c442069cbe762c7d3c78295b2d98e853bc6/packages/codemirror-vim-core/vim.js#L6415), [upstream issue 121](https://github.com/replit/codemirror-vim/issues/121).

**Evidence from an executable probe.** I ran the actual upstream Vim engine in Node with a minimal in-memory editor and DOM stubs. The probe wrapped `Vim.handleKey` to retain the source editor during execution and observed `pushText` without replacing its behavior. With the document `one yellow\none yellow\nthree`, all eight normal-command cases passed assertions in the final run:

| Input | Range observed at the register write, as half-open offsets | Interpretation |
| --- | --- | --- |
| `yy` | `[0, 11)` | First logical line including its source newline |
| `yw` | `[0, 4)` | `one ` |
| `yiw` | `[0, 3)` | `one` |
| `3yy` | `[0, 27)` | Entire three-line document, with no fabricated EOF offset |
| `"ayy` | `[0, 11)` | Explicit named-register yank still exposes the source range |
| `"_yy` | `[0, 11)` | The hook is entered, but the black-hole register must be filtered |
| `fy` | No register-write call | A motion containing `y` is not a yank |
| `y$` | `[0, 10)` | Characterwise text through the first line's end |

This is evidence for the interception point, not a browser test or proof of Obsidian compatibility. The probe used simplified editor geometry and did not cover visual blocks, pop-out windows, rendered Markdown, or interactions with installed plugins. An attempted Ex probe required an unimplemented `StringStream` in the stub; Ex conclusions above come from source inspection. The final passing probe was restricted to the eight listed normal-command cases. No runnable Obsidian Electron app was found at the repository smoke harness's default `/snap/bin/obsidian` location, and I did not claim a live-app test.

**Existing implementations and alternatives.** The similarly named plugins use different approaches, so their names alone are not a sufficient basis for choosing one.

| Option | Findings | Judgment |
| --- | --- | --- |
| Aleksey Rowan's **Vim Yank Highlight**, `vim-yank-highlight`, 1.0.8 | Listed for installation through Community Plugins; desktop-only manifest. Watches `vim-keypress`/`vim-command-done`, checks whether the command contains `y` or `Y`, reads a register, then reconstructs the range using longest-common-substring matching | Useful for a quick experiential trial; not my recommended permanent implementation |
| Kometenstaub's **Vim Yank Highlighter**, `yank-highlight`, 1.1.4 | Wraps register-controller `pushText` and reads the active editor selection. README says manual/BRAT installation and documents that expiry needs a later cursor movement | Better semantic trigger, but incomplete rendering/lifecycle behavior |
| **Better Vim**, `better-vim`, 1.2.2 | Wraps `pushText`, has duration/fade settings, and includes clipboard, list, and motion behavior. Its highlight still reconstructs positions with the earlier substring algorithm | Too broad for this request and does not eliminate the main range problem |
| CSS snippet or vimrc-only setting | CSS can style a range once another component marks it; it cannot infer a completed yank. Native Vim/Neovim hooks are not automatically available in CodeMirror's Vim emulation | Useful for appearance only, not the event/range implementation |
| Replace or bundle another Vim engine | Would take ownership of keymaps, state, and compatibility across existing Bob plugins | Disproportionate risk for a visual acknowledgement |
| Small Bob-owned plugin | Exact native ranges, isolated compatibility code, host CM6 rendering, local tests and deployment | Best fit for this environment |
| Upstream dedicated yank event | Cleanest eventual source of editor/range data | Worth proposing separately; no need to block the local feature on upstream adoption |

The Rowan plugin is particularly revealing. `src/main.ts` explicitly checks whether its collected command contains `y` or `Y`; `fy`, `ty`, or a non-yank involving register `y` can therefore pass the classifier. Its renderer then searches visible text and prefers an occurrence around or after the cursor. That is an inference about the copied source, not the source itself. Repeated Markdown rows, backward motions, appending into registers, and selections partly outside the viewport make the inference fragile. Blockwise support is a TODO. Its longest-common-substring implementation allocates a full two-dimensional array and visits every pair of characters: time and space grow with **visible text length × yank length**. That is an unnecessary cost for `yG` on a large note. The lifecycle also keeps handlers on previously visited adapters while unloading removes handlers from the currently active one. These are source-based weaknesses; I have not reproduced every consequence in Obsidian. [Rowan event handling](https://github.com/aleksey-rowan/obsidian-vim-yank-highlight/blob/914c83c508823a29796a1e271c91e9b88e1fb0d0/src/main.ts), [range reconstruction](https://github.com/aleksey-rowan/obsidian-vim-yank-highlight/blob/914c83c508823a29796a1e271c91e9b88e1fb0d0/src/markViewPlugin.ts), [matching algorithm](https://github.com/aleksey-rowan/obsidian-vim-yank-highlight/blob/914c83c508823a29796a1e271c91e9b88e1fb0d0/src/util.ts).

Kometenstaub's implementation demonstrates that a small `pushText` wrapper is practical, but it obtains the editor through global active-view state, renders a single range, and clears an internal decoration variable without an explicit repaint transaction. Its README acknowledges the resulting timeout limitation. Better Vim improves event classification, but retaining substring matching still discards available positional information. Neither should be copied wholesale. [Kometenstaub source](https://github.com/kometenstaub/obsidian-vim-yank-highlight/blob/31e8df9350da241dff70770b66730bf1cdcc16a2/src/main.ts), [documented limitation](https://github.com/kometenstaub/obsidian-vim-yank-highlight/blob/31e8df9350da241dff70770b66730bf1cdcc16a2/README.md), [Better Vim trigger](https://github.com/NilsGke/obsidian-better-vim/blob/fb3120a45420fc279feb483aff673cf608bff655/src/util/yankEvent.ts), [Better Vim renderer](https://github.com/NilsGke/obsidian-better-vim/blob/fb3120a45420fc279feb483aff673cf608bff655/src/markViewPlugin.ts).

**Recommended implementation shape.** Keep this in a small dedicated plugin rather than expanding `bob-navigation-hotkeys` or assigning an unrelated responsibility to `bob-vim-surround`. Both Bob and third-party Vim functionality can then operate independently, and disabling the highlighter is a clean rollback. Source belongs in `bob-plugins`; use that repository's validation and `bob plugins sync` deployment process when implementing. No Rust/bob-cli contract is required for this presentation feature.

Separate the code into two responsibilities: an adapter producing verified yank snapshots, and a CM6 extension displaying them. The boundary should carry the originating editor, document identity, an array of `[from, to)` ranges, character/line/block kind, and a monotonically increasing generation. Do not retain copied text beyond any immediate consistency check, and do not log it.

For the adapter, first inspect and probe the **installed Obsidian build**. A current upstream checkout is not proof of the bundled implementation. If the bundled build exposes a genuine range-bearing yank event, prefer it. Otherwise the most promising fallback is a narrowly scoped wrapper around the existing register-controller `pushText`, preserving the native implementation rather than replacing the yank operator.

The global register controller does not carry an editor argument, so a bare `pushText` wrapper plus `getActiveViewOfType(MarkdownView)` is insufficient. Establish the source adapter during native command execution. The inspected upstream path and Node probe support a `Vim.handleKey` wrapper with a synchronous stack and `try/finally`; if Obsidian executes returned `findKey` callbacks directly, scope those callbacks instead. Preserve `this`, arguments, result, exceptions, and nested mapping/macro execution. Do not install a second copy of `@replit/codemirror-vim` to get a convenient API: it would have different state from the engine handling the user's keys.

For stronger provenance, capture the per-editor selections when native `getSelection()` reads the text within that execution scope, then pair that fresh snapshot with the subsequent `'yank'` call. This avoids treating unrelated register writes or Ex `getRange()` calls as selection-based yanks. Consume the snapshot once and discard it on scope exit. Check document identity and that the selected text matches the text supplied to `pushText`, before register append/newline normalization. Such comparison verifies already-known positions; it does not search the document. Nested Ex mappings and callbacks need explicit regression coverage. If provenance cannot be established, omit the flash.

At the register hook, filter `operator !== 'yank'` and the black-hole register `_`. Capture synchronously while the prepared selections still exist; call the original method exactly once; schedule the visual effect only after the native call returns successfully. A decoration failure must never suppress or corrupt the yank. Do not swallow errors from the original operation, and do not assume an asynchronous clipboard promise has succeeded. Repeated yanks of identical text must flash again even though register contents are unchanged.

This is intentionally a compatibility adapter, not a claim of a fully public extension hook. Its exact wiring should be chosen by the installed-build probe. The additional `getSelection` provenance guard is a design recommendation, not something the small Node probe implemented or validated. Avoid replacing `Vim.defineOperator('yank', ...)`: in the inspected engine, `defineOperator` sets a private operator table and does not return the old operator. Reimplementing its behavior merely to add feedback creates avoidable maintenance around cursor restoration, registers, visual modes, and future fixes. [Vim API and operator registration](https://github.com/replit/codemirror-vim/blob/c3131c442069cbe762c7d3c78295b2d98e853bc6/packages/codemirror-vim-core/vim.js#L2948).

For rendering, register one CM6 extension through `registerEditorExtension`. A state effect can install/clear a snapshot; a view plugin can own the timer and build decorations for its visible ranges. Keep all timers and generations per editor. Defer painting until native command processing finishes, but never defer the range capture itself. If a queued effect finds a different document or a destroyed editor, drop it. On expiry, dispatch a real clear effect so the mark disappears even when the user does nothing. A generation check protects a newer flash from the previous timer.

Use half-open CM6 offsets and let the native adapter handle the zero-based Vim line positions. Clip EOF correctly: a register may receive a synthetic newline that has no document position. For linewise highlighting, do not accidentally include the next line when the selection ends at its start. Use actual per-row spans for visual blocks, including short rows and tabs. For a large yank, store its source interval(s) and decorate only their intersection with visible ranges, rather than creating a decoration for every hidden line. Preserve selection, viewport, folds, search decorations, and syntax styling. Ordinary cursor movement need not clear the flash; edits, document replacement, plugin unload, or editor destruction should.

Lifecycle cleanup must cover every mounted editor, windows, queued callbacks, timers, and wrappers. Use cooperative unwrapping or an established wrapper mechanism; unloading must not restore an obsolete function over another plugin's later wrapper. If a wrapper remains in another wrapper's chain, it must become inert after unload. Feature-detect adapter capabilities, retry at appropriate editor/Vim lifecycle boundaries, and provide one diagnostic if unsupported rather than a notice on every keypress. Keep one highlighter enabled during acceptance testing.

**Compatibility and acceptance checks.** Bob Vim Surround intercepts `ys` and injects its own operator. That is a concrete reason not to watch raw `y` keystrokes. Test `ysiw)`, `cs`, and `ds` alongside normal yanks. Vimrc Support's inspected clipboard integration watches register contents and can asynchronously read/write the system clipboard; highlighting should neither depend on that polling nor add a second clipboard policy. [Bob surround integration](https://github.com/bobs-org/bob-plugins/blob/87b28e1a60ee4aceca1f9f7094ffe06129b81485/plugins/bob-vim-surround/main.js#L747), [Vimrc clipboard handling](https://github.com/esm7/obsidian-vimrc-support/blob/1ff5d97afcf3161f202aa460697233d550f6aa3f/main.ts#L588).

Before shipping, require the following checks in an isolated real-Obsidian scratch vault, followed by a brief manual check with Bryan's normal plugin/theme combination:

| Check group | Cases and required outcome |
| --- | --- |
| Core scope | `yy`, `2yy`, `yw`, `y$`, `yiw`, `yi(`, backward yanks, `yG`, and the installed mapping of `Y`; exact native source ranges |
| Registers | Named and append registers, repeated identical yanks, `_`; no changed register/paste behavior, no black-hole flash |
| Visual selections | Character, line, and rectangular selections in both directions; separate block spans, no intervening text falsely marked |
| Negative controls | `fy`, `ty`, `ry`, `"yp`, `dw`, `cw`, cancelled/failed motions, and surround operators; no yank flash |
| Source geometry | Empty line, EOF without newline, wrapped text, emoji/UTF-16, tabs, repeated rows, folded sections, links and code in Live Preview |
| Lifetime | Second yank within 200 ms, no input after yank, immediate edit, tab/document switch, split pane, pop-out window, unload/reload, Vim toggle |
| Existing behavior | Cursor, selection, `p`, macros, mappings, dot-repeat, undo, search highlights, and Bob decorations behave as before |
| Cost | Large-note `yG` does no document substring search and adds no vault I/O or clipboard access; measure rendering overhead separately from the native yank |

The existing `bob-plugins` real-app smoke harness already uses an isolated vault/profile, an owned Electron process, and CDP; extend that approach for an integration test rather than testing against the live vault. Unit tests should cover normalization, generation cleanup, and original-method delegation, but mocks alone cannot establish event ordering or Live Preview appearance. [Existing real-Obsidian harness](https://github.com/bobs-org/bob-plugins/blob/87b28e1a60ee4aceca1f9f7094ffe06129b81485/scripts/obsidian-startup-smoke.cjs).

**Confidence and remaining uncertainty.** Confidence is high in the UX value, SASE's 200 ms contract, the weaknesses found in the inspected plugins, and upstream's selection-before-register-write ordering. Confidence is moderate in the proposed adapter until tested against the actual Obsidian version. I did not inspect Bryan's live plugin list or vimrc, establish the installed bundled CodeMirror version, or test mobile/pop-outs. Those are implementation acceptance tasks, not reasons to expand this research into clipboard or keymap redesign. Repository observations are pinned above: Rowan `914c83c`, Kometenstaub `31e8df9`, Better Vim `fb3120a`, Vimrc Support `1ff5d97`, Bob plugins `87b28e1`, CodeMirror Vim `c3131c4`, and SASE `7cc41d8`.

**Recommended solution.** Implement a small `bob-vim-yank-highlight` plugin with a **200 ms, per-editor CM6 decoration over the native yank ranges**. Prove the installed engine's range capture first, then isolate any necessary wrappers behind one adapter and keep the renderer on CM6's extension API. Include normal and visual yanks, preserve every existing editing and clipboard behavior, and suppress feedback when range provenance is uncertain. Treat a dedicated upstream yank event as the future simplification. Do not adopt a substring-matching highlighter or a broader Vim replacement for this feature.
