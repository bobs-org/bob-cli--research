# Ref tasks as ordinary tasks in area/project notes — research (`__mus`)

Independent research for the 5-researcher swarm on re-imagining ref-task
tracking: every ref note gets an area/project parent, ref tasks live in the
parent note's Tasks section, and ref tasks stop being special-cased.

## 1. How ref tasks work today (verified in this checkout)

### 1.1 Storage: task line co-located in the ref note

A modern ref note under `ref/` carries its reading task inline in the body,
generated by the Highlights pipeline
([note.rs](/home/bryan/.local/state/sase/workspaces/bobs-org/bob-cli/bob-cli_14/src/native/highlights_ref/note.rs)):

```text
- [ ] #task #ref [[lib/papers/x.pdf]] #hide ^ref
```

Three properties make it "special" by construction:

- `#hide` removes it from the `READY_QUERY` / `PENDING_QUERY` / `NEXT_QUERY`
  Dataview queries
  ([tasks/mod.rs](/home/bryan/.local/state/sase/workspaces/bobs-org/bob-cli/bob-cli_14/src/native/dataview/tasks/mod.rs)),
  which all contain `tags do not include #hide`. That single tag is why ref
  tasks never appear in the `^` pickers (today/pending/next catalogs) and
  never enter the normal review surface.
- The block ID is the constant `^ref` — unique only because there is at most
  one such line per note. Two ref tasks in one note would already collide.
- `#ref` (constant `PDF_TASK_KIND_TAG`) marks the kind inline.

### 1.2 Status sync: two sources of truth reconciled per note

Reading state is derived, never stored
([docs/ref.md](/home/bryan/.local/state/sase/workspaces/bobs-org/bob-cli/bob-cli_14/docs/ref.md),
[status.rs](/home/bryan/.local/state/sase/workspaces/bobs-org/bob-cli/bob-cli_14/src/native/ref_library/status.rs)):

1. Exactly one `^ref` tracker with a known mark maps checkbox → status
   (`[ ]` ready, `[*]` next, `[/]` wip, `[x]` read, `[-]` abandoned;
   `[?]` defers to frontmatter or targets `ready`).
2. Tracker move with unchanged frontmatter = `pending` (tracker wins);
   both moving = `conflict`. Otherwise frontmatter `status` (+ legacy
   `legacy_status`) decides, with diagnostics (`unknown_ref_mark`, counts…).

Crucially, **the tracker lookup is intra-note**: `status.rs` scans the ref
note's own body for the `^ref` line, and `mod.rs` reads `finished`/`added`
dates from it. The `blocked` overlay (`[?]`) also reads the in-note tracker.
`ref list --git-dates` runs `git log -G\^ref` per note. Everything assumes
task and note are in the same file.

### 1.3 The freshness/review system treats `^ref` as a separate species

- `TrackerKind::Ref` ([state.rs](/home/bryan/.local/state/sase/workspaces/bobs-org/bob-cli/bob-cli_14/src/native/freshness/state.rs))
  is parsed from the exact block ID `ref`.
- `scan.rs` builds a dedicated `trackers` collection: hidden exact-`^ref`
  rows from the all-task scan that pass every scope exclusion *except*
  `#hide`. Hidden `^prj` rows are deliberately excluded ("sync owns that
  tag").
- `state.rs` gives trackers a `REFERENCES` tier (vs `PROJECTS` for `^prj`),
  a `reference_interval` config override, and tracker-specific lane-due
  arithmetic. A never-confirmed Ready reference walks in REFERENCES, never
  NEW.

### 1.4 Parent today means "marker parent", not area/project

- `bob ref create` **already has** `-P/--parent` (default `obsidian_ref`),
  but it is documented as "Bare Obsidian note target for the marker parent"
  — the parent embedded in the PDF's Highlights marker, which flows through
  the marker projection into the ref note's frontmatter `parent`
  ([create.rs](/home/bryan/.local/state/sase/workspaces/bobs-org/bob-cli/bob-cli_14/src/native/highlights_ref/create.rs),
  [marker.rs](/home/bryan/.local/state/sase/workspaces/bobs-org/bob-cli/bob-cli_14/src/native/highlights_ref/marker.rs),
  [model.rs `render_with_projection`](/home/bryan/.local/state/sase/workspaces/bobs-org/bob-cli/bob-cli_14/src/native/highlights_ref/model.rs)).
  So the flag name the proposal wants (`--parent`) is taken, its short flag
  `-p` is taken by `--published`, and its current semantics (PDF marker
  routing) are load-bearing for the scan pipeline.
- `bob ref list -P/--parent` already filters by bare parent name
  ([ref_library/cli.rs](/home/bryan/.local/state/sase/workspaces/bobs-org/bob-cli/bob-cli_14/src/native/ref_library/cli.rs)).
  After the change its *semantics stay* but its *values change* (area/project
  names instead of marker-parent names) — a silent behavioral break for any
  saved filters/scripts.
- Project notes resolve parents via `parent: "[[...]]"` wikilink targets
  ([projects/scan.rs](/home/bryan/.local/state/sase/workspaces/bobs-org/bob-cli/bob-cli_14/src/native/projects/scan.rs)).
  There is **no alias mechanism** anywhere: no `aliases`/`project_name_aliases`
  handling in `projects/`, `capture/`, or `capture_project_note.rs`. That part
  of the proposal is genuinely new.

### 1.5 The `done/` move machinery already exists and is link-based

`collect_done` moves closed tasks into `~/bob/done/` files and repairs
outgoing/incoming links (`[[note#^block]]` →
`[[done/note_done#^block]]`), per its unit tests
([collect_done/tests](/home/bryan/.local/state/sase/workspaces/bobs-org/bob-cli/bob-cli_14/src/native/collect_done/tests/unit.rs)).
So a ref task that keeps a **stable unique block ID** survives the move as a
followable link — the raw material for remote status sync is already there.
What does *not* exist is any consumer that resolves "the task for ref note X"
outside note X.

## 2. Critique: is this a good idea?

**Yes — with adjustments. The direction is right; the proposal as literally
specified has four gaps that would break real flows.**

**What is good.** Co-location in area/project notes removes a genuine
second-class citizen: today a ref task is invisible to the `^` pickers, the
READY/PENDING/NEXT queries, `bob task reconcile`, pomodoro Task Links, and
dependency links, purely because of `#hide` + `ref/` residence. Users already
think of "read this paper" as a task like any other, and the REFERENCES-tier /
`reference_interval` / `pending`-`conflict` machinery is conceptually duplicated
with the ordinary lane system. Deleting it shrinks the mental model: one task
system, one review walk, one close gesture.

**Gap 1 — fire-and-forget capture cannot satisfy a required parent.**
`bob capture '<URL>'`, `bob gkeep pull`, and background `ref jobs` queue work
with no user present. Making `--parent` *required on `bob ref create`* does
not cover these paths at all: they never invoke `create` interactively, and
the intake PDF's marker (hence the future note) gets the default
`obsidian_ref` parent. A "required" flag at create time either breaks every
scripted caller or forces a meaningless default, defeating the requirement.
The requirement must attach at **note-creation time (`ref scan`/`sync`)**,
not at intake time — see §3.5.

**Gap 2 — the proposed `-p|--parent` collides twice.** `-P/--parent` already
exists on `create` with different (marker) semantics, and `-p` is
`--published`. The proposal's literal flag spec cannot ship. Fortunately the
existing `--parent` is *already the right pipe*: the marker parent flows into
the note frontmatter parent, so the change is "resolve `--parent` against
area/project notes, drop the default, require it at scan time" — no new flag,
but a semantic migration of an existing one (§3.2).

**Gap 3 — the done-file move destroys the sync's founding assumption.**
Today sync reads the tracker from the ref note body. After the move *plus* a
later `collect_done` archival, the task lives in `done/<area>_done.md` while
the ref note has no task at all. Nothing in the proposal says how the ref
note finds its task again. This needs an explicit pointer (frontmatter
`ref_task` link) plus vault-wide block-ID resolution — it is the hardest part
of the project, not a footnote (§3.3).

**Gap 4 — "remove all special-casing" would silently change the review walk.**
Ref tasks entering READY means entering the freshness walk (NEW → ROTTEN),
`note-ready-cap` counting, `bob plan` lane membership, and pomodoro-ledger
derivation. That is the *point*, but it has a volume consequence: every queued
paper becomes NEW-walk load immediately on migration day. The REFERENCES tier
and `reference_interval` die with the old model — decide explicitly whether
any reading-cadence distinction survives (I recommend: no; a read task is a
read task). Also `ref list`'s default reading-queue view and `ref show`'s
TASKS section need redesign once tasks live elsewhere (§3.6).

**One more consideration — backlinks vs. task residence.** An alternative
design would keep the task line in the ref note but drop `#hide` and teach
every consumer to include `ref/` (i.e., fix visibility, not residence). I
reject it: it preserves the real awkwardness (a task you must visit a
library note to work, two task homes, per-note `^ref` collision risk) while
capturing only half the benefit. Residence in area/project notes is the
correct call; the proposal's instinct here is right.

## 3. Adjustments and design decisions

### 3.1 Identity: unique block IDs with a `ref-` prefix (required, as proposed)

- Format: `^ref-<8 lowercase hex>` (e.g. `^ref-3f9a1c2e`), generated with the
  same randomness discipline as annotation `^h-…` IDs. Stem-derived IDs
  (`^ref-ea-graph`) read nicer but collide on re-imports/renames; random IDs
  with a vault-wide uniqueness check at write time are the reliable choice.
- `TrackerKind::from_block_id` changes from exact `Some("ref")` to
  `strip_prefix("ref-")` (keeping exact `ref` accepted read-only for legacy
  notes during migration). Every `== Some("ref")` site (`freshness/scan.rs`
  tracker collection, `ref_library/status.rs`, git-log `-G\^ref` patterns,
  annotation-task diagnostics text) must accept the prefix form.
- Keep the stored `#ref` tag on the task line (it is the kind signal and the
  Dataview/Tasks query hook); change only rendering (§3.7).

### 3.2 No new flag: evolve the existing `create --parent` (adjustment)

- Keep `-P/--parent NOTE` on `bob ref create` (marker parent → note
  frontmatter parent is already the plumbing). Changes:
  1. Resolve `NOTE` against area/project notes at create time when possible:
     exact stem match → `project_name_aliases` match → unambiguous
     substring? (No — fail closed with candidates. Silent fuzzy matches on
     task homes corrupt the task graph.)
  2. **Do not make it required at create time** (Gap 1). Instead: optional at
     create; **required at scan/sync note-creation time**. `scan` refuses to
     mint a ref note with an unresolvable/missing parent, printing the exact
     `bob ref adopt --parent <note> <ref>` repair command. A
     `--default-parent` config covers the fire-and-forget intake flow.
- The sase file-hook question (does sase inject the project name into the
  hook command string?) is a **cross-repo unknown in sase-org/sase** — I could
  not verify it from this checkout. Two outcomes, both fine: if the hook
  supports template variables, pass `--parent {{project}}`; if not, add one
  variable (project derived from the repo remote/dirname) — a small,
  well-scoped sase-side change. Either way the alias layer (§3.4) absorbs the
  `bob-cli` → `bob.md` mismatch.

### 3.3 Remote status sync: pointer + vault-wide resolution (the core design)

Add one frontmatter field on the ref note, written by scan/sync/migration:

```yaml
ref_task: "[[areas/reading#^ref-3f9a1c2e]]"
```

Sync resolution order for "the task of ref note X":

1. Parse `ref_task`. If the linked note/line still holds that block ID, use it.
2. Else search the vault for `^ref-xxxx` (block IDs are unique by
   construction) — this transparently follows `collect_done` moves into
   `done/`, renames, and task-line edits that keep the ID.
3. If unresolvable: keep the frontmatter-status fallback and emit the
   existing `conflict`/diagnostic machinery (it already knows how to report
   "tracker missing" states — reuse, don't reinvent).

Keep the existing pending/conflict reconciliation semantics unchanged; only
the *locator* changes from "same file" to "pointer + global block-ID index".
`dataview::scan_all_rich_tasks` already exposes `block_id` per task, so the
index is a filter over an existing scan, not a new subsystem. `ref list -g`
git-dates must switch its `-G` pattern from `^ref` to the concrete ID.

Consequence to accept: `ref scan`/`sync` and `ref list`/`show` become
vault-scan dependent for status. They already scan the vault (index build);
this adds one all-tasks pass. Fine.

### 3.4 `project_name_aliases`: symmetric, closed-world matching (as proposed, tightened)

- New optional frontmatter `project_name_aliases: ["bob-cli"]` honored on
  **both project and area notes** (the proposal says project notes; capture
  targets areas too, and the same mismatch class applies).
- Resolution order, case-insensitive, fail-closed: exact stem →
  exact alias → else error listing close candidates. Never substring-match.
- Set `project_name_aliases: ["bob-cli"]` on `~/bob/bob.md` as the seed value.
- Validate the field in `bob projects doctor`/equivalent: duplicates across
  notes (two notes claiming `bob-cli`) must error loudly at scan time, not
  misroute tasks.

### 3.5 Capture prompts: flag-first, prompt as TTY fallback (adjustment)

- `bob gkeep pull`: add `--parent NOTE` applying to all URL-routed items in
  the pull (batch CLIs must not prompt per item). No flag + no config default
  → items clip as today (marker default / configured default parent) and the
  note waits for `adopt`; never fail the pull.
- `bob capture '<URL>'`: same — accept `--parent`, else default-and-adopt.
  Its output already prints `→ reading queue`; extend to
  `→ reading queue (parent: <note> | unassigned: bob ref adopt …)`.
- bob-mac-capture (separate repo, thin client over `bob` JSON): add a
  project/area picker to the ref-capture sheet that passes `--parent` through
  to `create`/jobs enqueue. The `^` today/pending/next pickers need their
  ref-exclusion filters removed (§3.6) — that work lives in
  `bob-mac-capture`, keyed off whatever signal it currently filters on
  (likely `#ref` tag, `^ref` block ID, or `ref/` path prefix — the lead
  should confirm; all three signals change shape in this project, so the
  client change must land in lockstep).
- Interactive prompting only when stdin is a TTY *and* the caller asked for a
  ref import in the foreground (`create` without `--parent` + TTY → prompt
  with completion from area/project stems). Scripts never block.

### 3.6 Special-case removal checklist (the "think hard" inventory)

Remove / re-point, in this checkout:

1. `freshness/scan.rs` `trackers` collection + `tracker_candidate_visible`
   `#hide` exemption — ref tasks flow through ordinary READY/PENDING/NEXT
   queries once `#hide` is dropped from the generated line.
2. `freshness/state.rs` `TrackerKind::Ref`, REFERENCES tier arm,
   `reference_interval` override — delete; retire the config key with a
   "unknown key" warning, not a hard error (old configs must not crash).
   Keep `TrackerKind::Prj`/PROJECTS untouched (`^prj` stays in-note).
3. `ref_library/status.rs` + `row.rs` in-note `^ref` scan — replace with §3.3
   pointer resolution. Keep frontmatter/legacy derivation for notes with no
   `ref_task` pointer (zorg/legacy notes never had trackers).
4. Generated line in `highlights_ref/note.rs`: drop `#hide`, mint unique
   `^ref-<hex>`, write it into the **parent note's Tasks section** at
   scan/sync time instead of the ref note body. Annotation-task parser
   (`annotation_tasks.rs`) and its "expected … `^ref`" diagnostics accept the
   prefixed form.
5. `ref show` TASKS section and `ref find`/`list` rows: resolve the remote
   task and render it with its location (`area#^ref-…`, including `done/…`
   after archival). `list -P` keeps working — its values are now area/project
   names, which matches the proposal's intent; flag the value change in
   release notes.
6. `bob ref jobs` fallback text (`retry: bob ref create …`) — append parent
   guidance.
7. Anything matching tasks by `path starts_with ref/` for exclusion — search
   `ref/` path-prefix filters in capture/pickers before deleting; residence
   outside `ref/` is now the norm, so stale path filters would *hide the new
   normal case*.

Keep (invariants the user relies on that look special but aren't the target):

- URL-routing classifier + intake pipeline (unchanged entry points).
- Derived-Blocked `[?]`/`dependsOn` machinery — ref tasks gain it like any
  task; the `blocked` overlay in `ref list` should now read the *remote*
  task's mark.
- `collect_done` link repair — the enabler of §3.3; add a test pinning
  `^ref-<hex>` link repair into `done/`.
- Annotation `## Tasks` (`[h:: …]`) linkage — orthogonal; untouched.

### 3.7 Rendering: display-only icon, following the `#task`→`⌗` precedent (as proposed, specified)

`docs/task-tag-marks.md` is the exact pattern to copy: stored text unchanged
(`#ref` stays in the file), a CSS-mask glyph replaces the pill in Live
Preview/rendered views, cursor/click reveals raw text, session toggle
restores pills, JS mirror lives in bob-ledger-tools with conformance vectors.

- Glyph: Lucide-style **bookmark**, echoing "reading queue". Ink: the violet
  tag accent (`#prj`'s family) — it must not reuse red/orange/yellow/green/
  blue (lane/freshness meanings) or the teal `#task` identity hue, per the
  doc's own hue table. Bookmark-in-violet reads as "tagged reference" and
  stays legible on the red Blocked tint for the same reason the teal glyph
  does.
- Scope narrowly to exact whole `#ref` tags on task lines (same truthfulness
  rule as `#task`): prose mentions of `#ref`, non-task lines, and `#refs`
  never render the icon.
- The new block ID `^ref-<hex>` must *not* render anywhere special — block
  IDs are already dimmed by theme; no second icon.

### 3.8 Migration (existing open ref tasks)

One command, dry-run by default, under the `migrate-zorg` safety pattern
(lock → pre-sync → re-plan → no-clobber writes → verify → one commit →
post-sync):

`bob ref adopt [--parent NOTE] [REF…]` (new; also the ongoing repair command):

1. For each ref note with an open in-note `^ref` tracker and no `ref_task`
   pointer: resolve parent (flag → existing frontmatter `parent` if it already
   names an area/project → prompt/TTY → else skip with a named report, never
   guess).
2. Append the task line (same mark, same text, `#ref` + PDF link kept, `#hide`
   dropped, fresh unique `^ref-<hex>`) to the parent note's Tasks section;
   delete the in-note line (leaving a `Read: [[parent#^ref-…]]` pointer line
   is a nice touch — cheap, keeps the ref note navigable).
3. Set frontmatter `parent: "[[<area/project>]]"` + `ref_task` pointer.
4. Verify through the rebuilt index: every migrated note resolves its remote
   task; every new block ID is vault-unique.
5. Closed (`[x]`/`[-]`) ref tasks: leave the line in place (history), still
   set `parent`+`ref_task`? No — recomputing pointers for closed tasks has no
   consumer (nothing syncs a finished read). **Leave closed tasks untouched
   except rewriting `parent` to the owning area/project when known.**
   Cheaper, and the done-file problem never arises for them (they're already
   terminal).

Order of operations for the whole feature: aliases (§3.4) → pointer sync
(§3.3) → `adopt` migration (§3.8) → line-format flip (§3.6.4) → picker/filter
removal (§3.6.1–2, + mac-capture lockstep) → icon (§3.7). Each step is
separately shippable; the migration is the point of no return.

## 4. Recommended solution

Ship the proposal with the adjustments above, in this order:

1. **Aliases + parent resolution** (`project_name_aliases` on project *and*
   area notes, fail-closed, duplicate detection; seed `["bob-cli"]` on
   `bob.md`). Unblocks the sase hook regardless of how project injection lands.
2. **`ref_task` pointer + vault-wide block-ID resolution** in the ref library
   index, keeping pending/conflict semantics. This is the load-bearing piece
   that makes the done-file move safe — prove it with a test that closes a
   remote ref task, runs `collect_done`, and re-resolves from `done/`.
3. **`bob ref adopt`** migration (dry-run default, zorg-style safety), moving
   open ref tasks to parent Tasks sections with fresh `^ref-<hex>` IDs.
4. **Flip the generators** (`create`/`scan`/`sync` write remote tasks, no
   `#hide`) and **delete the freshness special-casing** (REFERENCES tier,
   `reference_interval`, tracker `#hide` exemption) with a config-tolerant
   deprecation.
5. **Capture UX**: `--parent` on `gkeep pull`/`capture`, TTY prompt fallback,
   mac-capture picker + filter removal in lockstep.
6. **Bookmark icon** for `#ref` per the task-tag-marks pattern.

Biggest risks to name in the plan: (a) the sase file-hook variable is a
cross-repo unknown — confirm in sase-org/sase before promising that
half of the work; (b) migration-day NEW-walk volume — consider migrating
parents first and tasks in batches, or accept one heavy review day;
(c) any saved `ref list -P <marker-parent>` filters and `obsidian_ref`
assumptions break — grep the vault/scripts for `obsidian_ref` before release.

Verdict: good idea, worth doing. The core insight — one task system instead
of two — pays off every review. Don't ship the literal spec (flag collision,
required-at-create, unaddressed done-move); ship §3–§4 instead.
