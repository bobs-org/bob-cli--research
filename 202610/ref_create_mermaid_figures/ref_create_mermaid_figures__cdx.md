**Mermaid diagrams in `bob ref create`: preserve the PDF pipeline and render diagrams as assets**

Independent research by **cdx**, 2026-10-17. Scope: the supplied screenshot, Bob's current source, upstream documentation and source, and local rendering experiments. No other researcher's report, transcript, or findings were consulted. This is implementation research; no Bob production code or vault content was changed.

Adding Mermaid support is a good idea. The best fit for Bob is to render explicit Mermaid code blocks locally into cropped PDF assets, then let the existing Pandoc/XeLaTeX pipeline typeset the document. My preferred renderer is a small operation using Bob's existing Python/Playwright browser infrastructure and a pinned official Mermaid JavaScript bundle. Keep the document renderer, reference identity, stamping, and installation workflow intact. The official Mermaid CLI is a useful prototype and a reasonable faster alternative, but Bob already has the infrastructure needed to avoid another Node/Puppeteer installation dependency.

I interpret “does convert mermaid syntax well” as “does **not** convert Mermaid syntax well”: the supplied screenshot visibly prints `flowchart LR`, arrows, and `<br/>` markup in a code block. There was no detailed implementation plan to review, so the critique below evaluates the feature proposal and the main plausible implementations.

**What the current implementation establishes.** I inspected bob-cli at commit `30bdfb8900be9cc7a24dc534e73f9e0712a2b5c7`.

The external Markdown route calls Pandoc with XeLaTeX, a table of contents, numbered sections, fonts, and Bob's Lua filters. Those filters handle inline-code breaks, listen cards, and return links; they do not transform Mermaid `CodeBlock` nodes. Printing the source is therefore expected behavior, rather than evidence that a diagram renderer is malfunctioning. The integration point is [`render_temp_pdf` in create.rs](https://github.com/bobs-org/bob-cli/blob/30bdfb8900be9cc7a24dc534e73f9e0712a2b5c7/src/native/highlights_ref/create.rs#L3224).

There are **two relevant Markdown render routes**. Vault-note snapshots use [`render_note_pdf` in profile.rs](https://github.com/bobs-org/bob-cli/blob/30bdfb8900be9cc7a24dc534e73f9e0712a2b5c7/src/native/highlights_ref/note_snapshot/profile.rs#L84): projected Markdown → Pandoc-generated `.tex` → separately invoked XeLaTeX. That route uses `commonmark_x-tex_math_dollars-emoji`, while the external-file route currently lets Pandoc infer its reader. The snapshot filter preserves code blocks and already handles ordinary image nodes. A change only to the external-file invocation would leave surprising differences between `report.md`, a vault-note snapshot, and the existing `-M` plain-render mode.

Bob also already has a pinned Python Playwright adapter, browser discovery including `BOB_CHROME`, local print assets, and browser PDF printing. Its Rust transport enforces a deadline and kills the adapter process group, including descendants. These are useful implementation components, not a reason to send Markdown through article extraction. See the [browser adapter](https://github.com/bobs-org/bob-cli/blob/30bdfb8900be9cc7a24dc534e73f9e0712a2b5c7/scripts/web_clip/web_clip_adapter.py), [PDF printer](https://github.com/bobs-org/bob-cli/blob/30bdfb8900be9cc7a24dc534e73f9e0712a2b5c7/scripts/web_clip/web_clip_render.py#L754), and [process supervision](https://github.com/bobs-org/bob-cli/blob/30bdfb8900be9cc7a24dc534e73f9e0712a2b5c7/src/native/highlights_ref/clip_adapter.rs#L168).

**Experiments and their limits.** I reconstructed the diagram visible in the screenshot, rather than finding or reading the underlying research document. Its graph contains nine nodes, two disconnected components, long labels, quoted edge text, and HTML-style line breaks. All probes ran outside the vault in disposable workspace scratch. They used Pandoc 3.1.11.1, XeTeX from TeX Live 2025/dev/Debian, Chrome 155.0.8059.79, Mermaid CLI 11.4.2 with its installed Mermaid 11.6.0, and librsvg 2.60.0. The separate Playwright probe used 1.62.0, matching Bob's declared dependency.

| Probe | Observed result | Implication |
| --- | --- | --- |
| Plain Pandoc → XeLaTeX | PDF contains the Mermaid source | Independently reproduces the missing transform |
| Mermaid CLI → fitted PDF | Success in approximately 2.45 seconds; one page, 600 × 115.92 points; labels extract with `pdftotext` | Direct browser-generated diagram PDFs are practical |
| Mermaid CLI → SVG → `rsvg-convert -f pdf` | Both commands succeed; all labels disappear, while boxes/arrows remain | Successful SVG conversion is insufficient validation |
| Lua replacement of the code block with the generated PDF image → Pandoc/XeLaTeX | Success; labels and surrounding prose remain extractable | PDF embedding works in the document pipeline |
| Same replacement → intermediate `.tex` → separate XeLaTeX | Success | Explicit on-disk PDF assets also work with the snapshot route's two-step architecture |
| Python Playwright + local Mermaid bundle → fitted PDF | Success in approximately 1.95 seconds; one page, 1146 × 200.88 points; all 12 checked label phrases present | Reusing Bob's existing browser stack is feasible without invoking Node at render time |
| Invalid Mermaid (`A -->` with no target) through CLI | Nonzero exit, diagnostic, no PDF created | There is an actionable failure to propagate |

These timings are single-run observations, not benchmarks. The Playwright context blocked browser network requests and loaded the existing Mermaid bundle from disk; the valid fixture attempted zero requests. This does not establish complete handling of hostile diagrams. The spike used the already installed Mermaid bundle, not a new production vendoring implementation.

The SVG had 16 `foreignObject` elements. Visual inspection of the converted PDF confirmed empty nodes and missing edge labels; its extracted text was empty. Direct PDF rendering retained the screenshot's line breaks under `securityLevel: strict`. Thus, disabling HTML labels or relaxing security should not be the first response to this example. This is a measured compatibility problem with the tested SVG conversion path, not a claim that every SVG converter or every Mermaid version loses text.

Two additional observations affect implementation:

- Chrome initially failed with **“Socket path too long”** under SASE's inherited per-agent temporary directory. Giving the browser a short temporary root fixed it. Bob already addresses this in [`ScratchDir`](https://github.com/bobs-org/bob-cli/blob/30bdfb8900be9cc7a24dc534e73f9e0712a2b5c7/src/native/highlights_ref/workdir.rs#L29), and the web adapter assigns that directory to its own `TMPDIR`. Reuse that behavior; creating the output PDF in scratch alone does not fix Chrome's inherited temporary-path setting.
- Fitting this wide left-to-right graph into a portrait page produced diagram word bounding-box heights around **5.85 points**, versus about 9.96 for the surrounding prose. Those are extracted glyph bounding boxes, not exact nominal font sizes. The result is complete and zoomable, but small at page scale. Rendering support cannot guarantee that arbitrary diagrams are pleasant to read on paper.

**Alternatives and tradeoffs.**

| Approach | Benefits | Costs and conclusion |
| --- | --- | --- |
| Bob-owned Mermaid transform + existing Playwright stack + cropped PDF | Reuses installed browser infrastructure, can batch diagrams, controls network access, preserves vector/text output and current document typesetting | Requires a pinned Mermaid bundle, asset packaging, and a small render operation. **Preferred for this repository.** |
| Bob-owned transform + official `mmdc` PDF output | Fastest route to a working patch; official implementation; already installed on this host | Adds a supported Node/Puppeteer/CLI installation contract on other hosts; version-specific flags and browser configuration; per-block launches are expensive. Good constrained alternative. |
| Vendor `pandoc-ext/diagram` unchanged | Existing AST-based filter with Mermaid/PDF support | Too broad and insufficiently aligned with Bob's failure, metadata, and asset-lifetime contracts. Adapt ideas, not defaults. |
| SVG intermediate with a separate PDF converter | Attractive vector format, useful for HTML/export | The actual screenshot-style labels disappeared in testing; introduces another converter. Not the default PDF route. |
| PNG intermediate | Simple embedding, faithful browser pixels | Loses selectable labels and zoom quality; large diagrams need substantial pixel resolution. A deliberate fallback only if vector output proves unreliable for a supported case. |
| Whole-document HTML/Chromium or Quarto migration | Broad authoring features and a natural JavaScript environment | Reopens typography, pagination, navigation, return links, and snapshot behavior. Disproportionate for this request. |
| Hosted diagram API or a new local rendering service | Removes local rendering work from the client, or centralizes it | Introduces document disclosure/network availability or service operation. A service is unnecessary for a local import command. |

Quarto demonstrates that this feature is conventional, but its documented default for non-JavaScript outputs is browser-generated PNG. That is not an argument to migrate Bob's document pipeline, particularly when direct PDF embedding worked here. [Quarto diagrams documentation](https://quarto.org/docs/authoring/diagrams.html).

The Mermaid CLI is a credible alternative, but pinning matters. On the research date, the npm registry reported `@mermaid-js/mermaid-cli` **12.0.0**, requiring Node **>=22.13.0**. The inspected upstream checkout, `f416ac5c6e42edd3a8be6d512c1008520d0c2f97`, fits diagram PDFs by default and exposes `--pdf-paper-format` for fixed paper sizes; it no longer has the installed 11.4.2 CLI's `--pdfFit` flag. Its Markdown extraction still uses a regular expression matching particular three-character fences, and its README says its Node API is outside its semantic-versioning guarantee. Do not copy an old `mmdc --pdfFit` command into an unversioned installation, or use its whole-Markdown rewrite as Bob's parser. [CLI implementation](https://github.com/mermaid-js/mermaid-cli/blob/f416ac5c6e42edd3a8be6d512c1008520d0c2f97/src/index.js), [package manifest](https://github.com/mermaid-js/mermaid-cli/blob/f416ac5c6e42edd3a8be6d512c1008520d0c2f97/package.json), [API caveat](https://github.com/mermaid-js/mermaid-cli/blob/f416ac5c6e42edd3a8be6d512c1008520d0c2f97/README.md#use-nodejs-api).

The inspected `pandoc-ext/diagram` checkout, `5aaf35e6f775ddf501045fe28b03642ee73db2f4`, makes several choices worth avoiding here. Its Mermaid engine invokes `mmdc --pdfFit` once per block. A conversion error produces a warning and leaves the source block in place. Optional caching hashes the source text without fully describing the rendering environment. Generated bytes go into Pandoc's media bag; the README calls for `--extract-media` to materialize assets, which matters for Bob's separate `.tex` compilation. Its documentation also warns that document metadata can select an executable unless configuration is constrained. These are specific integration concerns, not reasons to reject Pandoc filters generally. [Engine, cache, and error handling](https://github.com/pandoc-ext/diagram/blob/5aaf35e6f775ddf501045fe28b03642ee73db2f4/_extensions/diagram/diagram.lua), [usage and security contract](https://github.com/pandoc-ext/diagram/blob/5aaf35e6f775ddf501045fe28b03642ee73db2f4/README.md).

**Requirements I would adjust explicitly.**

1. **Define support as rendering explicit Mermaid code blocks.** Recognize Pandoc `CodeBlock` nodes with the `mermaid` class. Respect the selected Markdown reader's syntax, including supported tilde fences, longer fences, attributes, and nesting. Leave ordinary code and literal demonstrations untouched. Do not attempt to recognize every block containing `graph` or `flowchart`.
2. **Cover both Markdown routes.** Apply the transform after vault-note projection and before PDF layout, as well as to external Markdown. Keep `-M` as a layout/projection choice, not an undocumented Mermaid-off switch. Direct PDF imports remain simple imports.
3. **Require complete output or an explicit error.** Missing browser/bundle, invalid syntax, timeouts, and unsupported resource references should fail before PDF/audio installation. Do not silently produce a successful “rendered” PDF containing the source. Authors who want source displayed can use a `text` fence. A user-selectable best-effort mode can wait until there is demonstrated demand.
4. **Separate fidelity from page layout.** Preserve diagram direction and labels. Fit within the available line width and page height without clipping or distortion; move a figure to the next page when needed. Warn when the required scale is likely unreadable. Do not silently rewrite `LR` to `TB`, drop nodes, or promise automatic graph pagination. Shorter labels or splitting a graph are authoring remedies; landscape-page support is a later feature.
5. **Prefer selectable vector output, but avoid overpromising.** Test label extraction for supported diagram families. Browser PDFs can preserve text, as this experiment shows; embedding a PDF does not guarantee screen-reader structure, meaningful reading order, or interactive diagram links. Those are separate requirements.
6. **Keep the feature local and dependency-scoped.** Documents without Mermaid should not launch a browser or require its dependencies. Do not download JavaScript from a CDN or send diagrams to a service during conversion. Initial dependency provisioning may require network access; distinguish that from offline rendering after setup.
7. **Limit the first version.** Support built-in diagram families exercised by fixtures, light print styling, and bundled/local fonts. Exclude remote images/fonts, arbitrary HTML widgets, interactive callbacks, and third-party renderer plugins initially. Do not add PlantUML/Graphviz or change the PDF backend as part of this work.

**A concrete integration design.** Pandoc provides a useful boundary: a filter transforms the parsed document between the reader and writer. This avoids maintaining a second Markdown parser. Bob already uses Lua filters; a Rust-owned JSON AST pass is also suitable when the Rust process needs to supervise a batch renderer directly. [Pandoc filter model](https://pandoc.org/filters.html), [Lua filter behavior and ordering](https://pandoc.org/lua-filters.html).

For this repository I would favor **Rust orchestration over the Pandoc JSON AST**, followed by the existing Lua filters. It adds a parse/serialize pass but makes batching, typed errors, and reuse of the existing Rust subprocess supervisor straightforward. A tiny Lua replacement filter is sufficient for the embedding itself—the prototype used one—but putting all browser orchestration inside it would create another process-management path.

The proposed flow is:

```text
original Markdown, or projected.md after snapshot asset preparation
    → Pandoc parse with that route's existing reader settings
    → collect explicit Mermaid CodeBlocks from the JSON AST
    → one supervised render request for the document's diagrams
    → replace those nodes with ordinary images referring to scratch PDFs
    → Pandoc writer with existing code/listen, return-link, and note filters
    → existing XeLaTeX, stamping, audio, and installation workflow
```

Preserve Pandoc's API-version field and all untouched nodes. Use the same Pandoc executable for both passes. For the external-file route, retain the original file's resource directory even though the transformed AST lives in scratch. For snapshots, render only after projection/transclusion and asset preparation; preserve `projected.md` for diagnostics and the current narration contract. Keep diagrams in document order and carry a block ordinal and optional identifier into diagnostics. Accurate original source line numbers are useful only if the parser supplies a reliable mapping; do not fabricate them from rendered text.

The renderer can be a dedicated operation beside the existing adapter, implemented in a separate module. It accepts a list of diagram sources and controlled output IDs, starts one browser, and returns each PDF's scratch-relative path, dimensions, and structured errors. Use sequential pages or tightly bounded concurrency first. This is a renderer operation, not a URL-capture request: no Defuddle, remote article fetching, or reader-template conversion.

Vendor a tested official Mermaid release with its license and provenance. Materialize all required runtime assets through [`src/scripts.rs`](https://github.com/bobs-org/bob-cli/blob/30bdfb8900be9cc7a24dc534e73f9e0712a2b5c7/src/scripts.rs#L71), which already embeds the web adapter and vendor assets. Verify that the chosen bundle includes—or is packaged with—any chunks it loads; a developer's `node_modules` directory must not be a production dependency. The tested Mermaid 11.6.0 proves feasibility, not that this older version is the right production pin. Select and test the maintained release used by the implementation.

In each fresh rendering page, inject only the pinned runtime, pass diagram text as an argument to `mermaid.render`, await rendering and font readiness, measure the final SVG, and print a tightly bounded PDF with backgrounds enabled and no browser headers. Use a stable light theme and supplied fonts so HTML label measurements do not vary with the host. Ensure page dimensions and viewport agree; check the result really has one nonempty page rather than hiding overflow with an unconditional first-page-only export.

Set `securityLevel: strict` and keep security/resource limits under application control. Mermaid documents a protected `secure` configuration set for settings that diagrams must not override. Strict mode is **not** a network sandbox: independently block network requests and uncontrolled local-file access in the browser context, and fail clearly on unsupported external assets. Bound source size, diagram count, rendering time, and output dimensions. This is targeted containment for the new renderer; it does not claim that the entire existing Pandoc/TeX import pipeline is safe for arbitrary hostile Markdown. [Mermaid configuration schema](https://mermaid.js.org/config/schema-docs/config.html#secure), [security levels](https://mermaid.js.org/config/usage.html#securitylevel).

Write actual `.pdf` files under Bob's existing private short scratch directory. Retain them until all XeLaTeX passes finish. Preserve code-block identifiers on the replacement image without duplicating anchors; return-link handling currently treats images and code blocks differently from return-capable headings/divs, so do not invent a new surrounding identifier-bearing div without testing navigation. Let Pandoc escape image paths rather than interpolating source text into raw TeX.

Reuse the existing process-group deadline mechanism, with diagram-specific diagnostics instead of web-capture advice to check a network connection. Preserve the current installation boundary: render failures happen before final PDF/audio writes. Respect `BOB_HIGHLIGHTS_KEEP_WORKDIR` for debugging. Dry-run should retain its existing promise to skip Pandoc, XeLaTeX, and rendering; an exact diagram count is not worth breaking that contract. Doctor can report optional Mermaid runtime/browser availability without launching a full conversion or making non-Mermaid routes fail.

Do not add a persistent cache in the first patch. Deduplicating identical blocks within one document is sufficient initially. If a persistent cache later becomes justified, include the diagram text, Mermaid version, render configuration, font assets, renderer implementation version, and relevant browser version in its key—not source text alone.

**What should establish readiness.** The acceptance suite should exercise observable output and installation behavior, rather than merely checking that a browser command was invoked:

- The reconstructed screenshot becomes a diagram with all labels, arrows, both components, and line breaks; surrounding text, bookmarks, metadata markers, and return links still work.
- Flowchart, sequence, class/ER, and a larger chart exercise rendering and text extraction. Cover Unicode, quoted labels, symbols, and the chosen font fallback. Run a small real-browser suite on Linux and macOS; do not demand byte-identical PDFs across platforms.
- AST fixtures cover multiple/nested blocks, longer and tilde fences, supported attributes/IDs, and literal examples. Non-Mermaid documents do not start the renderer.
- Both direct PDF output and the snapshot `.tex` route embed files whose lifetime spans all compilation passes. Include spaces and non-ASCII characters in source/scratch paths.
- A missing bundle/browser, malformed graph, blocked external resource, excessive diagram size, and a hung worker produce clear errors with no final PDF/audio installation and no orphan browser. Include the long inherited `TMPDIR` regression.
- Wide/tall diagrams are not cropped or stretched. Inspect representative pages visually and check expected label text. The screenshot's roughly six-point glyph boxes make a useful readability stress case rather than an automatic “looks good” golden.
- Verify dry-run behavior, existing output collision handling, `-M`, snapshot narration source, and packaging from an installed binary rather than only a development checkout.

This research did not exercise the full Bob create/scan workflow, macOS Highlights selection behavior, every Mermaid grammar, or a newly vendored current release. The two successful pipeline probes establish feasibility, not production readiness. They also explain why a bare “PDF exists” assertion would miss the most serious observed failure.

**Recommended solution:** implement a shared Pandoc AST transform for both Markdown routes, backed by a batched local Mermaid renderer using Bob's existing Playwright/browser infrastructure and pinned official JavaScript. Embed cropped PDF assets into the current XeLaTeX pipeline, preserve labels and source files, and fail explicitly before installation when rendering cannot complete. Treat readable page layout as a tested requirement with honest limits. This delivers the requested feature with a small, well-defined rendering component; an `mmdc`-based version is the fallback if minimizing the initial code change is more important than reusing Bob's existing dependency stack.
